# 2. المعمارية والتقييم التقني

## 2.1 التصور المعماري العام (Offline-First Desktop)

النظام تطبيق سطح مكتب أحادي الجهاز، كل شيء محلي، مقسّم إلى طبقات صارمة الفصل:

```
┌─────────────────────────────────────────────────────────┐
│  Presentation Layer (شاشات + طباعة + ثيم Dark/Light)   │
│  - شاشات POS والإدارة (MVVM)                            │
│  - محرك قوالب الطباعة (حراري 80مم + A4/PDF)             │
├─────────────────────────────────────────────────────────┤
│  Application / Services Layer (منطق الأعمال)            │
│  - SalesService, PurchaseService, InstallmentService,   │
│    ShiftService, InventoryService, ReportService,       │
│    BackupService, AuthService, ApprovalService          │
│  - كل عملية مالية = Use-Case واحد = معاملة DB واحدة     │
├─────────────────────────────────────────────────────────┤
│  Domain Layer (الكيانات + قواعد العمل + الحالات)        │
│  - Vehicle, Invoice, InstallmentPlan, Shift, Voucher…   │
│  - آلات الحالة State Machines (حالة الوحدة/الفاتورة)    │
├─────────────────────────────────────────────────────────┤
│  Data Access Layer (Repositories + Unit of Work)        │
│  - SQL صريح أو ORM خفيف، Migrations مرقّمة              │
│  - معزولة تمامًا: تسمح بالانتقال لاحقًا إلى PostgreSQL  │
├─────────────────────────────────────────────────────────┤
│  SQLite (ملف واحد + WAL) + مجلد نسخ احتياطية            │
└─────────────────────────────────────────────────────────┘
```

**مبادئ إلزامية:**

1. **Unit of Work:** أي Use-Case مالي (حفظ فاتورة، تحصيل قسط، قفل وردية) ينفَّذ داخل معاملة SQLite واحدة `BEGIN IMMEDIATE … COMMIT`، تشمل: المستند + بنوده + حركة المخزون + حركة الخزنة/طريقة الدفع + سجل حركة الوحدة + سجل التدقيق. فشل أي خطوة = تراجع كامل.
2. **State Machines صريحة:** حالة الوحدة وحالة الفاتورة وحالة القسط تتغير فقط عبر انتقالات معرَّفة (الوثيقة 07 §B) — لا تحديث حر للحقول.
3. **لا حسابات في الواجهة:** الواجهة تعرض فقط؛ كل حساب (إجمالي، خصم، ضريبة، ربح، توزيع قسط) في طبقة الخدمات ومغطى باختبارات.
4. **الطباعة عبر قوالب:** كل مستند مطبوع له قالب (حراري/‏A4) بمتغيرات، وبيانات المعرض (اسم/شعار/عنوان/تليفون) من جدول الإعدادات.
5. **ساعة الجهاز مصدر الوقت** مع تسجيل تحذير في سجل التدقيق إذا رُصد رجوع الساعة للخلف عن آخر حركة مسجلة (حماية من التلاعب بالتاريخ).

## 2.2 تقييم SQLite لهذا المشروع

### هل SQLite كافية؟ **نعم، وبهامش أمان كبير.**

الحمل المتوقع (افتراض A12): آلاف الفواتير سنويًا، عشرات آلاف الصفوف سنويًا في أكبر الجداول (حركات مالية/أقساط). SQLite تتعامل بأداء ممتاز مع ملايين الصفوف وقواعد بعشرات الجيجابايت على جهاز واحد. عنق الزجاجة الوحيد المعروف لها — الكتابة المتزامنة من عدة عمليات/أجهزة — غير موجود هنا أصلًا (كاتب واحد: التطبيق نفسه).

### المميزات في سياقنا

- **ملف واحد** = نسخ احتياطي واستعادة ونقل على فلاشة ببساطة ملف.
- **صفر إدارة:** لا خدمة Server ولا Port ولا كلمة مرور قاعدة بيانات تُنسى؛ مثالي لعميل غير تقني.
- **ACID كامل** حتى مع انقطاع الكهرباء (بالإعدادات الصحيحة أدناه).
- مضمَّنة داخل التطبيق: الـ Installer لا يحتاج تثبيت أي شيء إضافي.
- أدوات فحص سلامة مدمجة (`integrity_check`, `quick_check`) ونسخ آمن أثناء التشغيل (`VACUUM INTO`, Backup API).

### القيود التي يجب معرفتها

| القيد | أثره علينا | التعامل |
|---|---|---|
| كاتب واحد في اللحظة (قفل على مستوى الملف) | لا أثر: تطبيق واحد على جهاز واحد | WAL يسمح بقراءة أثناء الكتابة (تقارير أثناء البيع) |
| لا يصلح للمشاركة عبر شبكة/مجلد مشترك (SMB) | **ممنوع منعًا باتًا** وضع الملف على مجلد شبكة — يسبب تلفًا | الملف على القرص المحلي فقط |
| لا مستخدمين/صلاحيات داخل قاعدة البيانات | الصلاحيات مسؤولية التطبيق (جدول users/permissions) | + تشفير اختياري (انظر أدناه) |
| أنواع بيانات مرنة (Type Affinity) | خطر إدخال نص في حقل رقمي | `STRICT` tables (SQLite ≥ 3.37) + CHECK constraints |
| `ALTER TABLE` محدود | تعديلات المخطط تحتاج أسلوب إعادة إنشاء الجدول | نظام Migrations مرقم منضبط منذ اليوم الأول |
| لا أمان للملف نفسه (يمكن فتحه بأي أداة) | بيانات عملاء وأرقام قومية على القرص | تشفير القرص (BitLocker) أو SQLCipher — انظر §2.4 |

### متى نحتاج PostgreSQL/MySQL لاحقًا؟

فقط عند تحقق أي شرط من هذه:
1. **أكثر من جهاز يعمل في نفس الوقت** على نفس البيانات (كاشير + مدير على جهازين).
2. **فرع ثانٍ** مع الحاجة لمزامنة مركزية أو تقارير موحدة لحظية.
3. الحاجة لوصول عن بُعد (صاحب المعرض يتابع من البيت عبر خادم).

عندها الانتقال المخطط له: طبقة Repository المعزولة + مخطط SQL قياسي (بدون خصائص SQLite حصرية في المنطق) يجعل الترحيل إلى PostgreSQL عملية نقل بيانات وتغيير Driver، لا إعادة كتابة. **لا تبنِ مزامنة «ملف SQLite مشترك» أبدًا كحل وسط.**

### 2.3 إعدادات SQLite الإلزامية (PRAGMAs)

تُنفَّذ عند كل فتح اتصال:

```sql
PRAGMA journal_mode = WAL;         -- مرة واحدة، تبقى في الملف: قراءة أثناء الكتابة + أمان أعطال ممتاز
PRAGMA synchronous = NORMAL;       -- التوازن الصحيح مع WAL (يظل ACID عند انقطاع الكهرباء؛ FULL يبطئ بلا داعٍ)
PRAGMA foreign_keys = ON;          -- إلزامي عند كل اتصال (لا يُحفظ في الملف!)
PRAGMA busy_timeout = 5000;        -- انتظار 5 ثوانٍ بدل فشل فوري عند تزامن داخلي
PRAGMA trusted_schema = OFF;
-- عند الإغلاق اليومي/قفل الوردية:
PRAGMA wal_checkpoint(TRUNCATE);   -- دمج WAL في الملف الرئيسي قبل النسخ الاحتياطي
PRAGMA optimize;                   -- تحديث إحصاءات المخطط
```

- **الجداول:** تُنشأ بـ `STRICT` وبـ `CHECK` على الحالات والمبالغ (`amount >= 0`).
- **المعاملات:** `BEGIN IMMEDIATE` للعمليات الكاتبة لتجنب ترقية القفل في منتصف العملية.
- **الفهرسة:** فهرس فريد على (شاسيه)، (موتور)، (نوع المستند + السنة + الرقم)، وفهارس على كل الأعمدة المستخدمة في التقارير (تاريخ، حالة، عميل، مورد) — القائمة الكاملة في الوثيقة 04 §14.
- **فحص السلامة:** `PRAGMA quick_check` عند بدء التشغيل (سريع)، و`integrity_check` كامل أسبوعيًا وقبل كل نسخة احتياطية مجدولة وبعد كل استعادة.

### 2.4 استراتيجية النسخ الاحتياطي والاستعادة (Backup/Restore)

**آلية النسخ:** الأمر `VACUUM INTO 'مسار/الملف.db'` — ينتج نسخة **متسقة ومضغوطة (بدون فراغات) وذاتية الاكتمال** أثناء عمل التطبيق دون إيقافه، وهي أفضل من نسخ الملف يدويًا (الذي قد يلتقط حالة غير متسقة مع WAL) ومن `.backup` (لأنها تضغط أيضًا).

**السياسة (قابلة للضبط من شاشة الإعدادات):**

| النوع | التوقيت الافتراضي | الوجهة | الاحتفاظ |
|---|---|---|---|
| تلقائي يومي | عند قفل آخر وردية أو أول تشغيل بعد منتصف الليل | `Backups/Daily/` محليًا | آخر 14 نسخة |
| تلقائي أسبوعي | الجمعة (قابل للضبط) | `Backups/Weekly/` | آخر 8 نسخ |
| تلقائي شهري | أول يوم بالشهر | `Backups/Monthly/` | آخر 12 نسخة |
| يدوي على فلاشة | زر «نسخة على فلاشة» | يختار المستخدم القرص | لا يُحذف تلقائيًا |

**تنسيق اسم النسخة:** `MotoPos_Backup_2026-07-05_2130_v12.db` (التاريخ + الوقت + رقم إصدار المخطط) + ملف `manifest.json` بجانبها (إصدار التطبيق، إصدار المخطط، عدد الفواتير، SHA-256 checksum).

**خطوات النسخة (تلقائية بالكامل):**
1. `wal_checkpoint(TRUNCATE)` ثم `VACUUM INTO` إلى ملف مؤقت.
2. فتح الملف المؤقت وتشغيل `PRAGMA integrity_check` عليه — فشل الفحص = النسخة تُرفض ويُنبَّه المستخدم.
3. حساب checksum وكتابة manifest ثم النقل للمجلد النهائي وتطبيق سياسة الحذف القديم.
4. تسجيل النتيجة في جدول `backups` وفي سجل التدقيق.

**الاستعادة (معالج 4 خطوات لغير التقنيين):**
1. اختيار ملف النسخة (من قائمة النسخ المكتشفة تلقائيًا محليًا وعلى أي فلاشة موصولة).
2. النظام يتحقق: integrity_check + توافق إصدار المخطط (لو النسخة أقدم: تُشغَّل الـ Migrations عليها تلقائيًا؛ لو أحدث من التطبيق: رفض برسالة واضحة «حدِّث البرنامج أولًا»).
3. عرض ملخص النسخة (تاريخها، عدد الفواتير، آخر فاتورة) + تحذير صريح: «سيتم استبدال البيانات الحالية، وسيُؤخذ منها نسخة أمان الآن».
4. **قبل الاستبدال يُنشأ Backup تلقائي للقاعدة الحالية** باسم `PreRestore_...` ثم يُغلق الاتصال ويُستبدل الملف ويُعاد فتح التطبيق. صلاحية الاستعادة لصاحب المعرض فقط.

**تشفير البيانات:** الافتراضي المقترح: تفعيل BitLocker على القرص (بدون تكلفة تطوير). البديل الأقوى: SQLCipher/SEE لتشفير الملف نفسه (يجعل النسخ الاحتياطية مشفرة أيضًا). القرار مطروح في الوثيقة 11 (سؤال Q6) لأنه يوازن بين الأمان وسهولة استرجاع العميل لبياناته لو نسي المفتاح.

### 2.5 هيكل الملفات على جهاز العميل

```

C:\ProgramData\MotoPOS\                ← البيانات (لا تُمس عند الترقية)
├── data\
│   ├── motopos.db                     ← قاعدة البيانات
│   ├── motopos.db-wal / -shm          ← ملفات WAL (تُدار تلقائيًا — لا تُنسخ منفردة أبدًا)
│   └── schema_version                 ← نسخة المخطط الحالية
├── backups\
│   ├── daily\  weekly\  monthly\  manual\  prerestore\
├── templates\                         ← قوالب الطباعة (فاتورة A4، ريسيت، عقد، جدول أقساط…)

├── logs\                              ← سجلات التطبيق (Rolling, 30 يوم)

```

## 2.6 مقارنة البدائل التقنية والتوصية

> **ملاحظة مهمة (تعارض مكتشف):** المستودع الحالي يحتوي على تطبيق **Flutter** مالي جاهز («حساباتي»: SQLite عبر sqflite، توليد PDF وطباعة، نسخ احتياطي تلقائي، قفل PIN، تقارير ورسوم). المتطلبات حصرت المقارنة في 4 بدائل لا تشمل Flutter. أضفنا Flutter Desktop كبديل خامس للمقارنة لأن تجاهله يعني إهدار خبرة وكود قائمين. الحسم النهائي سؤال Q1 في الوثيقة 11.

### جدول المقارنة (تقييم من 5)

| المعيار | 1) Electron + SQLite | 2) Python Desktop (PySide6) | 3) .NET 8 WPF + SQLite | 4) Local Web App (متصفح + خادم محلي) | 5) Flutter Desktop (Windows) |
|---|---|---|---|---|---|
| سرعة التطوير | 4 (نظام واجهات ويب غني) | 3 (واجهات Qt أبطأ بناءً) | 4 (XAML + مكتبات ناضجة) | 4 | **4.5** لفريق يعرف Flutter |
| سهولة الصيانة | 3 (تحديثات Chromium/Node مستمرة) | 3 (توزيع Python هش) | **5** (منصة مستقرة طويلة الدعم LTS) | 2.5 (طبقتان: خادم + متصفح) | 4 |
| سهولة التثبيت | 3.5 (Installer كبير 150–250MB لكنه مباشر) | 2.5 (PyInstaller كثير المشاكل مع مضادات الفيروسات) | **5** (Self-contained EXE واحد ‏≈80MB + Inno Setup) | 2 (خدمة + منفذ + متصفح = دعم فني أكثر) | 4.5 (مجلد EXE + Inno Setup) |

### التوصية النهائية

- **الخيار الأول: ‎.NET 8 + WPF + SQLite (عبر `Microsoft.Data.Sqlite` أو EF Core)** — الأعلى تقييمًا موضوعيًا لبرنامج POS على ويندوز: أفضل طباعة (وهي شريان النظام)، أسهل توزيع (ملف تنفيذي ذاتي الاكتمال + Inno Setup)، أداء وثبات وصيانة طويلة الأمد، وطريق ترقية طبيعي (نفس طبقة الخدمات تصبح Web API لو توسع المعرض).
- **الخيار الثاني (المكافئ عمليًا إذا كان فريق التطوير Flutter):** **Flutter Desktop Windows + sqflite_common_ffi/drift** — يفقد قليلًا في عمق الطباعة الحرارية مقابل مكسب كبير: خبرة الفريق الحالية، إعادة استخدام مكونات «حساباتي» (PDF، نسخ احتياطي، قفل، ثيمات)، وإمكانية تطبيق أندرويد لمندوب التحصيل لاحقًا من نفس الكود.
- **يُستبعد:** Local Web App (تعقيد تشغيل ودعم فني بلا مقابل على جهاز واحد)، وPython Desktop (أضعف حلقة في التوزيع على ويندوز)، وElectron (استهلاك موارد وحجم بلا ميزة حاسمة هنا).

> بقية الوثائق محايدة تقنيًا: قاعدة البيانات، القواعد، الشاشات، والتقارير تنطبق حرفيًا على أي من الخيارين المُرشَّحين. الوثيقة 10 §3 تقدم هيكل مشروع لكلا الخيارين.
